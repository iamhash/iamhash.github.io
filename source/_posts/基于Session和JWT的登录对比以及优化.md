## 基于Session的登录与会话保持

### Session介绍

Session是用户在访问网站时由服务器创建的会话对象，里面一般是键值对形式存储数据：

```
session = {
  "smsCode": "384729",
  "loginUser": UserObj,
  ...}
```

它会默认存在服务器内存中。（**Tomcat会在内存中维护一个Map存放所有的Session**）。

Java中，Session是通过HttpSession对象来存储和管理的。一般会由Servlet 容器（如 Tomcat）来自动创建：

```
HttpSession session = request.getSession();
```

而可通过session.getAttribute("key")、 session.setAttribute("key", value)来获取和设置属性。

共享Session情况：

- **同一用户在一次请求中产生的线程**：可以共享，多线程通过request.getSession()得到同一个Session对象
- **同一用户在不同请求中产生的线程**（比如前后两次请求）：可以共享，只要Cookie中`JSESSIONID`不变【后面会讲】，服务端就能实现同一个session。
- **不同用户请求**：不能共享。session是用户隔离，因此不同用户不能共享。
- **高并发多个线程访问同一session**：需注意线程安全。虽然`HttpSession`是线程安全，但多线程修改时最好加锁。

### 整体流程

1. 当从浏览器第一次访问网站时：用户发送 HTTP 请求，服务器检测到该请求中 没有携带 Session ID（如 JSESSIONID）。服务器会新建一个Session对象，并生成一个唯一的SessionId。
2. 在服务端的响应中设置Set-Cookie：服务器将这个 Session ID 放入响应头中的 **Cookie** 里发给用户浏览器，浏览器就会保存这个cookie。
3. 用户后续请求自动带上 Cookie：浏览器在后续访问时自动将 Cookie 发给服务器，服务器从这个 Session ID 找回之前创建的 Session 对象
4. 开发者存取 session 数据，Java中可使用HttpSession session = request.getSession();...这些数据会存在服务器的内存中,属于用户独享。
5. Session 在多个请求间保持：只要 Cookie 中的 JSESSIONID 没变，服务器就知道是同一个用户，所以用户刷新页面、提交表单、甚至换路由，服务器都能继续获取这个用户的会话数据。
6. Session 过期或销毁：Session 有默认的超时时间（例如 30 分钟），用户长时间不活动会自动销毁

### 项目中的使用

1. 由于项目是基于短信验证码登录，因此在生成验证码以后，会先将验证码保存至Session再发送给用户，当用户提交验证码时会和session中的进行校验进行判断。
2. 当校验验证码一致以后，会根据手机号查询用户是否存在：若用户存在，则直接保存该用户Id到Session方便后续去取；用户不存在的话，则创建新用户-->保存用户到数据库-->再保存用户到Session。

此时还需配置登录拦截器用于判断用户是否登录：

1. 首先自定义登录拦截器类，继承HandlerInterceptor，并在prehandle方法中定义处理逻辑。（后续会优化）
2. 配置完登录拦截器后还需将自定义拦截器注册进SpringMVC的拦截器列表中，才能生效。

## 使用Redis优化Session登录

在分布式集群环境中，会话（Session）共享是一个常见的挑战。默认情况下，Session是存在于服务器内部的，各个服务器都有各自的Session，服务器之间各自的Session是不可见的、不可共享的。因此会发生：**服务器集群共享Session问题**。

**为什么使用Redis解决：Redis是独立于各服务器之外的，因此Redis里的数据是所有服务器都可见的，所以使用Redis可以代替Session，以解决分布式集群环境的会话保持的问题**

### 基于Redis实现登录与会话保持：

首先明确这里的Redis两个作用：

- **登录验证**：发送验证码时将其保存至Redis，登录验证时从Redis取出与用户提交的参数对比
- **会话保持**：保存用户登录状态，将用户信息存储至Redis便于服务器中识别。

**这里要考虑的三点：**

**1、用什么数据类型     --String **

**2、key怎么设计   --要求每个用户的key都不同，因此可使用”phone:手机号“作为key**

**3、是否设置TTL及时间   --设置为3~5min即可，避免占用大量内存** 

会话保持：

存用户信息对象可以选择String或Hash数据类型，存对象时String与Hash的比较：

- String：以 JSON 字符串的形式保存对象，优点是**直观、操作简单**，但是 JSON 结构会有一些非必须的内存开销，比如双引号、大括号，内存占用比 Hash 更高，不支持单独对属性字段的修改
- Hash：以 key—value（field、value）形式保存对象，**可以对单个字段进行CRUD，更加灵活**

选型：如果对内存占用不在乎，且想要直观简单，可以使用String；如果从优化的角度，可以选Hash

**核心逻辑：**

登录验证：**这里的key选用“phone:手机号”来保证每个用户的唯一性。**首先生成验证码后，将其保存至Redis中。校验时同样从Redis中来取。

会话保持：**这里的key选用随机token存储用户数据来保证安全性。当下列操作执行完毕后，需要给客户端返回token，便于验证登录状态。**当判断成功并且手机号查询到用户存在，直接保存用户到Redis；若不存在，同样的先创建用户-保存到数据库-写入redis

这里还需配置拦截器：

- 一是为了校验用户的登录状态
- 二是若用户始终活跃，则保持用户的登录状态，即**重置Redis中用户信息(可理解为登录凭证)的TTL**

若只用一个拦截器来实现，那么假设用户已登录，并且它只在首页等一些路径白名单进行活跃，因此不会触发TTL重置，那么到期后他的登录状态还是会被清除，因此违背初衷。

因此需要两个拦截器：

**第一个拦截器：刷新登录态拦截器，对所有路径生效，他的职责就是如果携带了合法token那么就刷新登陆状态TTL，无论是否登录，都放行**。并且若存在则将用户信息放在ThreadLocal中方便后续来取。

拦截器二：校验登录态拦截器，判断是否登录，若未登录则拦截，登录成功才放行。

注意：这里再第一个拦截器中刷新token有效期：

```
//重置 Redis 中某个 key 的过期时间（TTL）
stringRedisTemplate.expire(token, LOGIN_USER_TTL, TimeUnit.MINUTES);
```

## 基于JWT（JSON Web Token）登录

### JWT介绍

不同于基于Session登录是服务端进行状态存储，jwt登录是客户端进行状态存储（无状态）。

### 登录流程

1. 用户通过用户名加密码登录以后，服务器验证成功并会签发一个JWT Token将用户信息封装进去（比如userId等信息）
2. 客户端拿到token会存储在Cookie或LocalStorage中。
3. 后续请求时，会将Token放入请求头中（Authorization）。
4. 服务器解析Token，验证合法性（验证签名、是否过期），再提取用户信息进行处理。

【服务端无需保存任何状态，只要验证 Token 即可（适合分布式场景）】

优点：1.无需共享状态，天然支持微服务架构。2.服务端无状态，压力小

缺点：1.每次请求都携带 Token，体积较大。2.Token 泄露风险大。

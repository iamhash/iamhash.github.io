## 缓存的运用

### 什么是缓存？

缓存是数据交换的缓冲区（称作Cache）。这里的读写性能很高。

但可能也会有一些成本：数据一致性成本、代码维护成本（解决缓存三大问题的成本）、运维成本（集群模式）

### 为什么要用到缓存

某些信息变动频率很低，契合缓存读多写少的场景。虽然可能还是会修改，但就涉及到一致性问题与缓存三大问题。

### 创建、查询缓存通用模板

举一个最基本的业务，当我们要根据id去查询某个数据时，通常都会用到以下几个步骤：

1. 构建key，从Redis中获取对象数据。
2. 判断缓存是否命中（使用StrUtil.isNotBlank(对象)判断缓存是否为空），命中则直接返回数据。
3. 若未命中，则去数据库中查询。判断数据库中是否能查询到数据。（使用LambdaQueryWrapper构建数据库查询条件）
4. 若数据库中不能查询到，则直接返回失败信息。
5. 若数据库能查询到则先写入Redis中再返回。

【若Redis中存储的是Json数据，需要注意在存入和取出时的数据格式转换：

```
JSONUtil.toBean(studentJson, student.class);//取出时 转换为具体对象类型

JSONUtil.toJsonStr(student)；//装入时 转换为Json类型

typeList = JSONUtil.toList(studentTypeJSON, studentType.class);取出时 转换为List<T>类型
```

】

### 数据一致性处理

采用TTL过期作为兜底方案，同时将缓存和数据库的操作放到同一个事务来保障操作的原子性 (单体项目)

```
// 4.2 数据库中若存在，重建缓存，并返回店铺数据
    stringRedisTemplate.opsForValue().set(key, JSONUtil.toJsonStr(student), CACHE_student_TTL, TimeUnit.MINUTES);
```

更新时也要先更新数据库，再去删除缓存。

## 缓存穿透问题以及解决

### 什么是缓存穿透？

这里最重要的是`透`这个字，穿透即客户端请求的数据在**Redis缓存和数据库**中都不存在，这样缓存都不生效，请求都会打到数据库中。

### 为什么会发生

缓存机制一般为“有就返回、无则查库并缓存”。如果数据库查不到数据，通常什么也不缓存。当下次访问同样的key时又会重复这个循环。

### 解决方案1：缓存空值

核心思路：当在数据库中查询不到数据时，将空结果缓存起来，例如：

```
key: user:99999999
value: null 或者 一个特殊标记，比如 "__NULL__"
```

注意：最好**设置一个较短的 TTL（过期时间）**，避免一直占用缓存。如果是暂时不存在的数据，将来数据库有更新也能够重新加载

**优点：实现简单，维护方便；缺点：额外内存消耗，短期可能不一致。**

这样之后，再次请求相同ID时：会先查询缓存，发现是空值就不会再访问数据库，直接避免了数据库的无谓查询。

**细节**：

这里**判断缓存是否命中**使用的是 if (StrUtil.isNotBlank(studentJson)){...返回店铺数据...}

判断缓存中**查询到的数据是否是空字符串**：if (studentJson != null){..返回错误信息....} //相当于以前打在数据库中的全都打在这里了

而在查询了数据库发现不存在以后，应当：

if (Objects.isNull(student)) {
        // 数据库中不存在，缓存空值（解决缓存穿透）
        stringRedisTemplate.opsForValue().set(key, "", CACHE_NULL_TTL, TimeUnit.MINUTES);

### 解决方案2：布隆过滤器

布隆过滤器是一种空间效率极高的概率型数据结构，用来判断某个元素是否存在于一个集合中。

优点：内存占用较少、没有多余key。

缺点：实现复杂、存在误判可能、无法删除数据。

将布隆过滤器加在客户端和Redis中间，用来在最前面高效拦截非法请求，避免请求进入缓存和数据库，从源头防止缓存穿透；而缓存空值是兜底机制，减少真实请求中对不存在数据的重复查询。
两者搭配使用是应对缓存穿透的最佳实践之一。

**布隆过滤器如何解决缓存穿透？**

在系统初始化或数据变更时，我们将所有**合法的用户 ID（或其他查询主键）**都加入布隆过滤器中，请求处理逻辑如下：

```
if（!bloomFilter.mightContain(requestId)) { 
/ / ID 肯定不存在， 直接返回 null， 不查缓存也不查库  
return null;
//否则查缓存——>查数据库。（走正常路径）
```

布隆过滤器（但存在误判）内存占用很小，适合大规模数据；而缓存空值（但内存占用大）无误判，返回真实缓存结果。

## 缓存雪崩问题以及解决

### 什么是缓存雪崩？

雪崩，意思就是大量的数据，也就是指**同一时间段大量缓存key失效或Redis服务宕机**，导致大量请求打在数据库，带来巨大压力。

### 解决方案

- 给不同的key的TTL添加随机值
- 利用Redis集群提高服务可用性
- 给缓存业务添加降级限流策略，使得请求尽可能打不到数据库上。
- 给业务添加多级缓存

## 缓存击穿

### 什么是缓存击穿？

缓存击穿（击，指的就是大量攻击一个，也就是热点key的大量请求）也叫热点key问题，是一个**被高并发访问并且缓存重建业务复杂（因为会导致查询数据库的时间较长）**的key突然失效，无数的请求访问会给数据库带来巨大的冲击。

### 常见解决方案1：基于互斥锁

互斥锁：多个线程并行执行，只有一个线程加锁成功，其他线程均失败。

加互斥锁的时间是当缓存不存在并需要构建的时候。首先需要获取互斥锁，获取成功则执行数据库操作；获取失败则阻塞。

在获取锁后，查询数据库并将数据写入Redis后便释放锁。

```java
   // 4.实现缓存重建
        String lockKey = LOCK_SHOP_KEY + id;
        try {
            boolean isLock = tryLock(lockKey);
            if (!isLock) {
                // 获取锁失败，已有线程在重建缓存，则休眠重试
                Thread.sleep(50);
                return queryWithMutex(id);
            }
            // 获取锁成功，根据id查询数据库
            shop = this.getById(id);
            // 模拟重建的延时
            Thread.sleep(200);
            // 5. 判断数据库是否存在店铺数据
            if (Objects.isNull(shop)) {
                // 数据库中不存在，缓存空值（解决缓存穿透）
                stringRedisTemplate.opsForValue().set(key, "", CACHE_NULL_TTL, TimeUnit.MINUTES);
                return null;
            }
            // 6. 数据库中存在，重建缓存，并返回店铺数据
            stringRedisTemplate.opsForValue().set(key, JSONUtil.toJsonStr(shop),
                    CACHE_SHOP_TTL, TimeUnit.MINUTES);
        } catch (InterruptedException e) {
            throw new RuntimeException(e);
        }finally {
            // 7. 释放互斥锁
            unlock(lockKey);
        }
```

获取互斥锁的方式：

```
 /**
     * 获取锁
     */
    private boolean tryLock(String key) {
        Boolean flag = stringRedisTemplate.opsForValue().setIfAbsent(key, "1", 10, TimeUnit.SECONDS);
        // 拆箱要判空，防止NPE
        return BooleanUtil.isTrue(flag);
    }
```

细节：

1. 这里通过setnx是否执行成功来判断获取锁是否成功。释放锁即是将该key删除。
2. 锁的有效期更具体业务有关，需要灵活变动，一般锁的有效期是业务处理时长10~20倍
3. 线程获取锁后，最好再次查询缓存（双重检查）

### 常见解决方案2：基于逻辑过期解决

缓存击穿的原因还是由于热点key的TTL过期，若不设置TTL，便会避免缓存击穿。但TTL一般会设置，因此可用缓存逻辑过期：

在Value中加一个过期时间字段（还是使用JSON字符串表示），在获取key时检查过期时间字段是否过期，发现过期则加互斥锁，开启独立线程去重建缓存，本线程暂时返回旧数据。其他线程获取key->发现过期->获取互斥锁失败->暂时返回旧数据

一般搞活动时，比如抢优惠券，秒杀等场景，请求量比较大就可以使用逻辑过期，等活动一过就手动删除逻辑过期的数据。

#### 代码实现

代码实现步骤：首先定义RedisData类，里面包含存储的数据和expireTime过期时间，这些都是要存储在Redis中的数据。接着对实现逻辑过期的方法进行编写：大致模板还是首先构建key并从Redis中查询数据，未命中直接返回，若命中检查是否缓存过期（从查询到的对象中得到过期时间数据，使用JSONUtil.toBean（）来转换）若未过期则返回，若过期则获取锁，获取锁成功则开启独立线程进行缓存重建，获取锁失败也返回过期店铺信息。

【**为什么逻辑过期反而缓存未命中才返回？**

**逻辑过期的核心思想**是：缓存中依然保留旧数据，但额外加一个字段 expireTime（过期时间）。在读取缓存时：

- 如果当前时间 < expireTime：说明数据还没过期，可以直接返回。
- 如果当前时间 ≥ expireTime：说明数据逻辑上已过期，此时可以返回旧数据，同时触发异步更新操作（比如加锁去查数据库并刷新缓存）。

而设置逻辑过期不同于TTL过期，因此每次查询到缓存需要去和当前时间判断是否过期，否则可能会取到过期的老数据。

若缓存根本没命中，说明key根本不存在，这时说明是真正的缓存穿透/击穿，要么是数据库中没数据（返回空值防止穿透），要么是热点数据刚好被清理了（击穿）。而这针对的是热点数据，因此没查到就直接返回空

】

**因此逻辑过期一定要先进行数据预热，将热点数据加载到缓存中。否则会直接走到返回空的逻辑。**只有预热了热点数据，他才会进行缓存命中，从而去判断是否过期并进行后续逻辑。

**测试**：先进性数据预热，设置10s过期时间。等待逻辑过期后，使用JMeter压力测试，使用1s内并发100个线程并发，可以发现前面获取到的数据都是旧数据，直到缓存重建完毕后后面获取到的都是新请求。因此会有一小段时间不一致。

- 互斥锁：优点：保证一致性；缺点：线程需等待，性能受影响。
- 逻辑过期：优点：线程无需等待，性能好；缺点：不保证一致性
- **可用性和一致性的抉择(CAP定理)**：
  - 互斥锁保证了一致性，牺牲了可用性；
  - 逻辑过期保证了可用性，而牺牲了一致性。
